# 基于 Agentic AI 的金融长上下文推理、图谱穿透与财报反欺诈智能问答系统

> 技术文档写作大纲（比赛提交版）

## 1. 项目概述

### 1.1 项目背景

- 金融数据来源多、结构异构、时间跨度长，传统问答难以完成跨表和跨来源推理。
- 财务风险识别需要同时结合财务报表、股东关系、风险公告和券商研报。
- 大语言模型在金融场景中存在数值计算错误、口径混淆、证据缺失和幻觉风险。

### 1.2 赛题目标

- 构建面向金融研究的证据约束智能问答系统。
- 支持财务长上下文推理、有限股权图谱穿透和财报反欺诈线索发现。
- 输出可追溯、可审计、区分事实与待核实线索的分析结论。

### 1.3 系统定位与边界

- 系统定位：金融风险线索发现与证据问答系统。
- 不将模型输出作为审计结论或法律结论。
- 公告正文、实际控制链和合并报表缺失时，系统必须明确拒答。

### 1.4 主要贡献

1. 证据约束的单 Agent 工具编排框架。
2. 面向三张财务报表的跨期、跨表推理流程。
3. 基于股东名称反向索引的有限图谱穿透。
4. 版本化持久证据记忆与长上下文 ContextBuilder。
5. 确定性计算、口径校验和来源审计机制。

## 2. 数据集与问题建模

### 2.1 数据来源

| 数据域 | 文件/表 | 用途 |
| --- | --- | --- |
| 多轮问答 | `data/1` | 上下文依赖和问题分解 |
| 前十大股东 | `data/2` / `shareholders` | 股东关系和共同股东发现 |
| 风险公告 | `data/3` / `announcements` | 监管、处罚、整改和担保线索 |
| 财务报表 | `data/4` / 三张财务表 | 财务趋势和反欺诈分析 |
| 券商研报 | `data/5` / `research_reports` | 外部观点和风险提示交叉验证 |

### 2.2 数据清洗与标准化

- Wind 证券代码标准化。
- 日期统一为 `YYYYMMDD`。
- SQLite 表结构、索引和字段别名。
- 缺失值处理：空值不能视为 0。
- 报表口径标识：母公司、合并和未知口径的区分。

### 2.3 问题类型划分

- 单表单跳：指标查询、第一大股东、最新现金流。
- 跨期比较：同比、差额、趋势和阶段变化。
- 跨表勾稽：收入、利润、现金流、资产负债指标联合判断。
- 图谱穿透：共同股东、股东进入/退出和持股变化。
- 外部证据交叉验证：公告与研报对照财务数据。
- 边界/拒答：公告正文、实际控制人、合并报表等数据不足问题。

## 3. 总体技术路线

### 3.1 技术路线总览

```text
用户问题
  -> 实体、时间、指标和关系识别
  -> ContextBuilder 召回长期证据
  -> Agent 规划查询和计算步骤
  -> 财务/图谱/公告/研报工具执行
  -> 确定性计算与口径校验
  -> Evidence Auditor 审计证据完整性
  -> 输出结论、来源、置信度和待核实事项
```

### 3.2 设计原则

- 模型负责规划和解释，代码负责查询、计算和边界检查。
- 事实必须绑定原始来源，分析观点必须标记为观点或预测。
- 多表结论必须先取得各表数据，再按报告期对齐。
- 长上下文采用检索和压缩，不直接堆叠全部历史文本。
- 对数据不足进行可引用拒答，而不是猜测补全。

## 4. 系统架构

### 4.1 逻辑架构图

```text
                    +----------------------+
                    |      前端工作台       |
                    +----------+-----------+
                               |
                    +----------v-----------+
                    |   Agent Orchestrator  |
                    +--+-------+--------+--+
                       |       |        |
          +------------+       |        +-------------+
          |                    |                      |
  +-------v-------+  +---------v---------+  +---------v----------+
  | ContextBuilder|  |  Deterministic     |  | Evidence / Boundary |
  | 长上下文记忆   |  |  Query & Compute   |  | Auditor             |
  +-------+-------+  +---------+---------+  +---------+----------+
          |                    |                      |
  +-------v--------------------v----------------------v-------+
  | SQLite 财务表 · 股东表 · 公告表 · 研报表 · 证据账本       |
  +-----------------------------------------------------------+
```

### 4.2 Agent 编排循环

- 当前问题分析。
- 查询计划生成。
- 多表/多期工具调用。
- 查询结果写入任务级和持久化记忆。
- 计算工具执行同比、差额、趋势和比例。
- 结论生成与来源引用。
- 达到步数、查询数和 token 上限时安全终止。

每次运行可通过 `InvestigationRun` 生成结构化审计产物，保存工具调用、工具返回、计算输出、证据来源和引用验证结果；模型内部 reasoning 不写入该产物。

`analyze_question` 在运行产物外包一层稳定服务协议，统一处理空问题、运行失败和成功响应，为后续 HTTP 接口提供兼容边界。

当前已提供可选标准库 HTTP 适配器，公开 `/health` 与 `/api/analyze`，通过依赖注入接收 Agent runner，不增加 Web 框架依赖。

### 4.3 为什么采用单 Agent + 工具编排

- 当前任务重点是证据可靠性而非 Agent 数量。
- 单一推理状态减少多 Agent 间的信息丢失和结论冲突。
- 将财务计算和数据边界交给确定性代码，更容易测试和审计。
- 后续可按需要把复杂检索模块升级为专家 Agent。

## 5. 长上下文技术方案

### 5.1 长上下文问题定义

- 跨年度财务指标需要保持时间序列。
- 股东、公告、研报与财务数据需要跨来源关联。
- 长研报摘要和历史分析不能全部放入单次 Prompt。
- 上下文中存在“相似但不同期间”和“母公司/合并口径”陷阱。

### 5.2 三层记忆模型

1. **任务级工作记忆**：当前问题的查询签名、证据和中间计算。
2. **持久化证据记忆**：公司、表、期间、字段值、来源和数据版本。
3. **原始数据层**：SQLite 中可重新查询的财务、股东、公告和研报记录。

### 5.3 证据账本设计

- 主键：数据集版本 + 原始 source。
- 字段：公司、表名、期间字段、期间、字段值、来源、观察时间。
- 同一来源的多次查询自动合并字段。
- 数据库变更后生成新版本，旧证据不参与当前召回。

### 5.4 ContextBuilder

- 从问题识别证券代码和主题词。
- 按财务、股东、公告、研报主题召回候选事实。
- 按实体、期间、数据表和来源稳定排序。
- 在 token 预算内裁剪上下文。
- 保留每条事实的原始 source。
- 记忆缺失或问题要求最新值时回查原始表。

### 5.5 长上下文可靠性策略

- 防止 lost-in-the-middle：核心证据置于上下文高优先级位置。
- 防止时间混淆：显式记录报告期和期间口径。
- 防止来源漂移：事实和分析分离保存。
- 防止记忆污染：数据版本隔离。
- 防止上下文膨胀：字段级合并、去重和 token 预算。

## 6. 财务多表推理

### 6.1 报表对齐

- 使用 `s_info_windcode + report_period` 对齐利润表、资产负债表和现金流量表。
- 年报、半年报和季度累计口径分别标记。
- 不同报告口径不直接做趋势判断。

### 6.2 确定性计算工具

- `calculate_change`：差额和同比变化。
- `calculate_ratio`：比例和占比。
- `classify_series`：递增、递减、持平和波动。
- 空值保护和除零保护。

### 6.3 典型反欺诈信号

- 增收不增现。
- 应收账款或存货增速明显高于收入。
- 利润增长与经营现金流背离。
- 利润过度依赖投资收益或公允价值变动。
- 短期债务增加但货币资金和经营现金流恶化。

### 6.4 结论分级

- 已确认事实。
- 高风险异常。
- 待核实线索。
- 数据不足。

当前实现的 `financial_risk_signals` 只输出方向背离和增速比较结果，并保留公式与限制说明。风险等级、Beneish/Altman/Piotroski 阈值和 Ground Truth 在业务规则确认前不自动启用。

`financial_risk_signals_from_records` 进一步把查询记录按报告期对齐，并为每个信号记录实际使用的数据库来源，避免计算结果脱离原始证据。

评测运行产物可通过 `evaluation_metrics` 聚合工具成功率、证据覆盖率、未支持引用数量和运行错误率；答案准确率不由系统擅自生成，仍依赖人工 Ground Truth。

## 7. 图谱穿透技术

### 7.1 图谱关系模型

```text
股东 --持有--> 上市公司
上市公司 --发布--> 公告
上市公司 --发布--> 研报
上市公司 --拥有--> 财务报表
```

### 7.2 共同股东查询

- 先获取目标公司的前十大股东快照。
- 按股东名称反向查询其他上市公司。
- 返回股东、其他公司、持股日期和比例。
- 同名交叉只作为待核实线索。

### 7.3 图谱边界

- 不把同名当作同一法人。
- 不从第一大股东直接推断实际控制人。
- 不在缺少控制链时输出控制关系结论。

## 8. 证据约束与准确性控制

### 8.1 来源引用协议

- 数据库证据必须包含原始 `_source`。
- 公告标题不能替代公告正文。
- 研报预测必须标记为分析师观点。
- 母公司报表不能表述为合并报表。

### 8.2 工具层校验

- 字段白名单和别名映射。
- 查询重复检测。
- 最大步骤数和最大数据查询数。
- 空值、除零和未知字段错误处理。

### 8.3 计划中的 Evidence Auditor

- 检查结论是否有对应证据。
- 检查期间和报表口径是否一致。
- 检查是否把预测、同名关系或标题证据升级成确定事实。
- 检查置信度是否与证据完整度匹配。

当前已落地来源审计：`jrkj.evidence_verifier.verify_citations` 检查最终答案引用是否来自当前 Agent Run 的工具输出，并在 trace 中记录 `evidence_verification` 事件。它不把同名股东升级为控制关系，也不代替金融业务规则判断。

## 10. 实验设计

### 10.1 实验问题

1. 多表工具是否降低跨表问题拒答率？
2. ContextBuilder 是否提升跨期和长上下文问题正确率？
3. 证据账本是否降低来源缺失和数字漂移？
4. 股东反向索引是否提升共同股东发现能力？

### 10.2 对照组

- Baseline：单表、无长期记忆 Agent。
- Multi-table：支持多表和确定性计算。
- Long-context：加入版本化证据记忆和 ContextBuilder。
- Full prototype：加入图谱穿透和证据审计。

### 10.3 测试集设计

- 单表/单跳题。
- 跨期比较题。
- 跨表勾稽题。
- 股东穿透题。
- 公告/研报交叉验证题。
- 数据边界与拒答题。

### 10.4 评测指标

| 指标 | 定义 |
| --- | --- |
| 答案正确率 | 与人工参考答案一致的题目比例 |
| 数值准确率 | 数值误差在设定阈值内的比例 |
| 证据完整率 | 结论有对应可定位来源的比例 |
| 口径识别准确率 | 正确识别母公司/合并/累计口径的比例 |
| 拒答准确率 | 数据不足时正确拒答的比例 |
| 幻觉率 | 无证据事实或错误扩展结论的比例 |
| 平均延迟 | 单题端到端响应时间 |
| Token 成本 | 平均 Prompt、Completion 和总 Token |
| 上下文压缩率 | 原始候选证据与最终 Context Pack 的大小比例 |

### 10.5 消融实验

- 移除长期证据记忆。
- 移除 ContextBuilder，仅保留原始查询结果。
- 移除确定性计算工具。
- 移除报表口径校验。
- 移除股东反向索引。

## 12. 技术攻关脉络

### 12.1 第一阶段：单表基线

- 建立 SQLite 数据库和单表查询 Agent。
- 发现 API 失败、工具重复调用和最终回答缺失等问题。

### 12.2 第二阶段：多表推理

- 放开多表查询。
- 增加确定性计算和报告期口径判断。
- 解决收入、利润、现金流和资产负债的联合分析。

### 12.3 第三阶段：图谱穿透

- 增加股东名称反向索引。
- 用同名匹配发现共同股东线索。
- 明确同名不等于同一主体的边界。

### 12.4 第四阶段：长上下文记忆

- 建立版本化证据账本。
- 实现跨问题证据召回。
- 实现 ContextBuilder 的主题检索、排序和预算裁剪。

### 12.5 第五阶段：前端与证据审计

- 提供金融研究工作台。
- 接入实时 Agent trace、证据流和上下文检查器。
- 实现结论与证据的一致性审计。

## 13. 局限性与后续工作

- 公告正文尚未解析，暂不能回答处罚原因和责任人。
- 数据以母公司口径为主，合并报表能力不足。
- 股东同名匹配需要工商主体或统一社会信用代码进一步核验。
- 研报摘要存在长度和信息缺失问题。
- 需要扩大人工标注集并进行统计显著性分析。
- 后续可加入向量检索、知识图谱数据库和 PDF 原文解析，但必须保留结构化证据约束。
